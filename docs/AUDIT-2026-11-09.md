## The short list: what breaks trust

1. **Approving a bill wrote no audit row and answered with an error.** The audit entry used the bill number ("BL-004") where the database wants an id, so the insert was refused after the approval had already been saved (`src/app/api/projects/[code]/bills/route.ts`). Found while closing route gaps.
2. **The review-queue route decided any record by id.** It did not check the project, and it could accept a hand-recorded result, skipping the "not your own" rule and the data checks (`src/server/review.ts:17`).
3. **No organization check anywhere.** Projects resolve by code alone. Harmless with one organization, a cross-organization read and write with two (`src/server/auth.ts:156`).
4. **Changes with no audit row:** field records and stock, month close, the project's donor rules (choose, custom, decide, approve), Kobo connect and disconnect, donors and their deadlines, bill recording and vouchers, project creation.
5. **Translation sends raw field notes to the AI** and asks for people's names in English; the English becomes the record with no label and no confirmation (`src/server/translate.ts:26,73`). Against `docs/DATA-PROTECTION.md`.
6. **Photos go to the AI**, though the data protection note says files never do; the AI's "cannot be recognised" reading lifts the consent requirement with no audit row (`src/server/photo-coach.ts:46`, `src/lib/photos.ts:119`).
7. **Story drafts send interview notes raw** and overwrite a hand-written story (`src/server/stories-store.ts:76-79`).
8. **Report downloads treat "pre-flight still loading or failed" as zero blockers**: no warning, no DRAFT mark (`src/components/progress/preflight-page.tsx:226-243`).
9. **Screens that say "nothing to do" when their load failed:** Work, Closeout (`src/components/tasks/use-rows.ts:64`, `procurement/closeout-page.tsx:31`).
10. **Donor name, report deadline, spending and exchange rate each live in more than one place** (table 1).
11. **Decisions where a written ROP rule exists but is not shown, or the app does less than the rule:** who resolves a policy exception, purchases continuing during a donor conflict, share links from an unreleased report, payment approval above $25,000 (table 5).

## 2. Routes

### Routes, first half

Notes that apply to every row (read once):

- **Sign-in**: every route below except the two cron GETs calls `requireViewer` (src/server/auth.ts:144). It answers 401 when not signed in or the second step is owed, 403 for "View as" on writes (`write: true`), 403 when `allow` fails, and 403 when the path is `/api/projects/<code>/...` and the person is not on that project (auth.ts:156-157). `src/server/guard.ts` `handle()` only turns exceptions into a 500 JSON; it does no access check.
- **"single-org"** in the Org column means: there is no organization on the `Viewer` and no query filters by the caller's organization. `projectByCode` (src/server/field-store.ts:12-16) looks a project up by its globally unique code only; `people()` (auth.ts:132-136) returns all active staff; the HR ledger is one book per deployment (`HR_BOOK`, src/server/hr-store.ts:19). The code says so itself: "Single organization in the pilot" (src/server/project-store.ts:65). With one organization in the database nothing leaks. With a second one, every row marked single-org would let org A read or change org B's rows. Severity today: none; the day a second organization is added: breaks trust.
- **Project membership is default-open**: `onProject` (auth.ts:163) treats a person with an empty `projects` list as being on every project. By design, but it means the project check only bites for people an administrator has listed on specific projects.
- **Unknown project code** on any `/api/projects/[code]/...` route throws in `projectByCode` (field-store.ts:14) and comes back as a 500 with "Run npm run db:seed", and is recorded as a server error on the health page (guard.ts:14-15). Should be a 404. Cosmetic. `[code]` is never format-checked in the routes of this half.
- **HR-ledger routes** (expenses, hr, leave, onboarding, offboarding, payroll): every change is one appended entry in the hash-chained `hr_ledger` (hr-store.ts:72-75), which is the audit record. Marked "yes (ledger)".

**What `draftStructured` does not do, and so each caller must remember:**

- **Scrub.** `facts` is `unknown`; nothing checks it. Six callers scrub some fields by hand, three send free text raw (jobs 1, 3, 4).
- **Voice.** Each caller pastes `ROP_VOICE` into its own system prompt. Seven do; `opportunities-store.ts:75` and `ai-drafts.ts:32` write prose without it.
- **Audit.** It does not know who is asking or for which project. Fifteen different action names are written by callers, some with the model and some without; job 2 writes none.
- **Limits.** `aiAllowed` is called in ten routes and three stores, and skipped for jobs 2 and 15.
- **Failure.** Four copies of the same catch block, each slightly different; errors are thrown as bare `Error`, so routes cannot tell "try again" from a bug and most let them become status 500 server errors.

#### Proposal: `src/server/ai.ts`, one exported call

```ts
/** Text that has been through scrub(), or was passed on purpose with a stated reason. */
export type Cleared = { readonly __cleared: unique symbol; value: unknown; how: "scrubbed" | "as-is"; why?: string };

/** Walks any value and runs withoutNames over every string. Keys in `keep` are left alone (codes, ids, dates). */
export function scrub(value: unknown, keep?: string[]): Cleared;
/** For the few jobs that must send the thing itself: a donor agreement, a photo, text to translate. The reason is audit-logged. */
export function asIs(value: unknown, why: string): Cleared;

export type AiJob =
  | "translate" | "photo_coach" | "story" | "assistant" | "qpr_sections" | "qpr_claims"
  | "monthly_review" | "lens_review" | "procurement_document" | "procurement_check"
  | "setup_design" | "setup_terms" | "setup_budget" | "kobo_mappings" | "spend_columns"
  | "photo_post" | "opportunity_brief";

export type AiFailure = { ok: false; reason: "not_set_up" | "limit" | "timeout" | "busy" | "key_rejected" | "unreachable" | "declined" | "cut_off" | "empty"; message: string; retry: boolean };

export async function runAi<T extends z.ZodType>(job: {
  job: AiJob;                       // names the audit row and the limit count
  by: string;                       // the person; required
  projectId: string | null;         // required, null for organization-level jobs
  system: string;
  voice: boolean;                   // required, no default: true appends ROP_VOICE
  task: string;
  facts: Cleared;                   // a plain object does not compile
  schema: T;
  effort?: "low" | "medium" | "high";
  maxTokens?: number;
  timeoutMs?: number;
  images?: { type: "image/jpeg" | "image/png" | "image/webp"; data: Buffer; cleared: Cleared }[];
  documents?: { name: string; pdfBase64?: string; text?: string }[];
  countsTowardLimit?: boolean;      // default true; false only for background work
  detail?: Record<string, unknown>; // extra fields for the audit row
}): Promise<{ ok: true; out: z.infer<T>; model: string; runId: string } | AiFailure>;

/** The person's choice about a run: accepted, edited, dismissed, approved. Ties the decision to the proposal. */
export async function recordAiChoice(exec: Exec, run: { runId: string; projectId: string | null }, by: string, choice: string, detail?: Record<string, unknown>): Promise<void>;
```

What `runAi` does inside, in order, so no caller can skip a step:

1. No key → `{ ok: false, reason: "not_set_up", message: "AI is not set up here. Ask an administrator." }`.
2. Calls `aiAllowed(by)` (moved in from the routes) unless `countsTowardLimit` is false.
3. Appends `ROP_VOICE` when `voice` is true.
4. Builds the one client (module-level, the only `new Anthropic` in the repo) and the one stream call, with the one timeout and the one catch block, including the 529/500/too-large cases missing today.
5. Writes one audit row, `ai_run`, with `{ job, by, model (the one that answered), runId, cleared: how, why, outcome }`, on success and on failure.
6. Returns a result, never throws for an expected failure, so every route can show `message` and keep what the person typed.

Two guards make it a door and not a suggestion: an ESLint `no-restricted-imports` rule that allows `@anthropic-ai/sdk` only in `src/server/ai.ts`, and the `Cleared` type on `facts`.

Existing audit action names (`qpr_ai_drafted`, `ai_drafted`, …) can stay as they are for `lib/audit.ts`; `runAi` adds the uniform `ai_run` row beside them, and `AI_ACTIONS` in `limits.ts:15` can go.
