## The eight principles, as rules you can check

Tucker's brief: human-centered and AI native, every data point or document entered once, Apple-level UX on a robust technical base, ethical, impactful, efficient, effective, and it guides people toward key decisions using what ROP has learned. Each one becomes a test:

1. **Entered once.** Every fact has one place where a person enters it and one place it is stored. Every other screen, report and export reads it. A second input for the same fact is a bug. An upload is read once and its values carry their source.
2. **AI native, human decides.** AI does the reading, drafting, checking and mapping. A named person confirms. No AI output is saved as final. Every AI output shows its source and a plain reason. Every AI action is in the audit log.
3. **One next step.** Every screen answers "what do I do now?" with one primary action. No dead ends: every empty state, error and blocked action says what to do and links there.
4. **Phone first.** Works at 380px wide with one thumb. Loading, empty and error states exist on every screen that fetches.
5. **Robust.** Every API route checks who is asking, checks they belong to this organization and project, validates its input and writes to the audit log on any change. Money and counts are computed in one function each, never twice.
6. **Ethical.** `docs/DATA-PROTECTION.md` holds without exception. Names and identifying answers never reach the AI. Consent limits what leaves the app. Sex-disaggregated numbers are never silently summed.
7. **Guides decisions.** Where ROP has a rule or a lesson (policy layers in `src/lib/policy.ts`, the procurement blueprint, the build spec, lessons in `progress/learning`, market windows), the app shows it at the moment of the decision with the evidence beside it. **Never invent an ROP best practice.** If a decision has no written ROP rule behind it, list it in the morning report as a question for Tucker.
8. **Plain words.** A field officer reading in their second language understands every label. No development jargon. All four languages.

## Guardrails. These are absolute.

- **Never push to `main`. Never merge into `main`.** All work goes on `surge/2026-11-09` and its item branches. Push only those branches.
- **Never run `npm run db:migrate`, `db:seed`, the `staff` or `plan` CLIs, or anything else that writes to the database.** Generate migrations with `npm run db:generate` and commit them. Tucker applies them when he merges.
- **Migrations are additive only:** new tables, new nullable columns, new indexes. No drops, no renames, no type changes. If a cleanup needs one, write it up in the morning report and do not do it.
- Never print, copy, edit or commit `.env.local` or any secret.
- Never force push, delete a branch, rewrite history or run `git clean`.
- Never call a live outside service to test: no Kobo sync, no emails, no notifications.
- Synthetic data only. The sandbox project is `SFTP-2026`.
- **Keep the Do-not-touch list** in `docs/CURSOR-PROMPT-2026-11-09.md`. Cleanup means fixing and simplifying. It never means removing, hiding or merging a feature or an AI job.
- New dependencies: `vitest` only. Anything else goes in the morning report as a suggestion.
- **Never weaken a check to get green.** No `as any`, no `@ts-ignore`, no `eslint-disable`, no deleted or loosened test, no commented-out validation.
- Keep every house rule in `docs/CURSOR-PROMPT-2026-11-09.md` (i18n in four languages, voice rules, audit log, phone first).

## How to work unattended

- **Do not ask questions. Do not wait for a go.** Where the Cursor prompt says "wait for my go", write the short plan into the log and carry on. Where a choice could go either way, take the more conservative one and record it under Decisions in the log.
- One branch per item off `surge/2026-11-09`, named as in the build list. When lint, typecheck, build and tests all pass, commit, merge into `surge/2026-11-09` and push.
- **Three strikes.** If an item will not go green after three real attempts, leave its branch unmerged, write what blocked it in the log and move on. Do not let one item eat the night.
- Keep `docs/SURGE-LOG.md` current: after each item, one entry with time, what changed, what was decided and anything Tucker must look at. Commit the log with the item.
- Use subagents for wide read-only sweeps (the audits in Phase 2). Do the edits yourself so two agents never write the same file.
- Before changing a file over 600 lines, read all of it.
